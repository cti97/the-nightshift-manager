# M6 — the steward

Spec §7 (roles), §8 (dynamic capabilities), §10 (sandbox), §15 (API), §18 (build order).

M6 is the always-on box: a Raspberry Pi that runs the reflex path, keeps the private lane alive at
3am, advertises what it can reach, probes the cloud endpoint, and serves a read-only copy of the
board when the VPS is down. Plus the two things that make a fleet installable rather than
hand-assembled: `nsm agent install` and a signed `/dist` channel.

## Task 1 — the reflex executor (done)

`internal/agent/reflex.go`, `--executor agentic|reflex`. One provider call, no tool definitions, no
sandbox; an empty answer fails the run; the settle is checked against the budget like the loop's.
Provider construction was extracted to `providerDeps` so both executors share one implementation of
the auth_ref rules.

Acceptance: `TestReflexIsOneCallWithNoTools`, `TestReflexRefusesAnEmptyAnswer`,
`TestReflexFailsOverBudget`, `TestAgentRunChoosesTheExecutor`.

## Task 2 — `nsm agent install` (done)

Launchd agent (macOS) and systemd **user** unit (Linux), a wrapper that sources a `0600` env file,
and `--print`. The token never appears in a unit file or plist: those are world-readable and travel
into every backup of the machine.

Acceptance: `TestTheUnitFilesCarryNoSecret`, `TestInstallRefusesAnUnquotableToken`,
`TestTheLaunchdPlistIsWellFormed`, `TestTheSystemdUnitRestartsAndIsPerUser`,
`TestInstallPrintWritesNothing`.

## Task 3 — dynamic `lan:*` capabilities (done)

`internal/agent/lan.go`, `--lan service=host:port,…`. Each heartbeat dials each service and declares
`lan:<service>` only while it answers. The dial is the promise: nothing speaks SMB or CUPS, and a
deeper check would be a lie a placement decision could act on.

Acceptance: `TestLanProbeSpecIsStrict`, `TestReachabilityIsADial`,
`TestTheHeartbeatDeclaresOnlyReachableServices`.

## Task 4 — the endpoint canary (done)

**Files:** `internal/board/canary.go`, `internal/board/http.go`, `internal/agent/canary.go`,
`cmd/nsm/main.go`.

Shipped in `internal/board/canary.go` and `internal/agent/canary.go`. Two rules survived review and
are worth keeping: **a canary may only demote** (a 401 from a reachable service is not health, and
only the manager's authenticated probe may say `ok`), and **health events are written on change**
(a minute-by-minute probe would otherwise add 1,440 rows a day per endpoint).

The Pi probes the cloud endpoint on a schedule *from its own network path* — the whole point is that
it reaches the endpoint the way a node would, which the VPS cannot test for it. The board gains
`GET /canary` (node auth: the endpoints a steward may canary, with base_url and provider) and
`POST /canary/{id}` (node auth: `{ok, latency_ms, reason}`), which flips `endpoints.health` and
writes exactly one event per *change*, not per probe. The agent gains `--canary 60s`.

Acceptance as built: `TestAnUnreachableCanaryMarksTheEndpointDown`,
`TestTheSecondUnreachableReportWritesNoEvent`, `TestASuccessfulCanaryDoesNotPromoteTheEndpoint`,
`TestACanaryForAnUnknownEndpointIsAnError`, `TestTheCanaryListCarriesNoAuthRef`,
`TestTheCanaryWaitsForTheThreshold`, `TestTheCanaryReportsARecoveryOnce`,
`TestTheProbeTellsUpFromBroken`, `TestTheCanaryLoopStopsWithItsContext`,
`TestAgentRunTakesACanaryInterval`. The planned "from another node is refused" test was dropped:
`/canary/{id}` names an endpoint, not a node's claim on it, so there is nothing per-node to fence.

## Task 5 — the read-only replica (done, whole-file)

Built as `GET /admin/snapshot` (`VACUUM INTO`, admin only) plus `nsm replica serve`, which pulls on an
interval, verifies the download opens as a board, swaps it atomically, and serves it through
`HandlerReadOnly` — a guard in front of the whole mux rather than a list of safe routes, so a route
added later cannot become writable on the replica by omission.

**The audit the memo asked for: it passes.** Every `UPDATE work_items` that changes `status` has an
`AppendEvent` in the same function (`Claim`, `Report`, `Escalate`, `Decide`, `StartRun`,
`reapItem`); the one site without an event (`heartbeatInRange`) extends a lease, which no board
column reads. So the board view *is* derivable from events, and the memo's "project events, no
snapshot" decision stands for a future replica that needs sub-minute freshness.

The implementation still ships whole-file snapshots rather than an event projection: it is a few
hundred lines instead of a projection engine, and the freshness bound an operator needs (a minute) is
met by the pull interval. The event projection becomes worth building when the board's write rate
makes a full copy expensive, and the audit says it will not be blocked when that day comes.

Acceptance: `TestASnapshotIsAReadableBoard`, `TestSnapshotNeedsTheAdminToken`,
`TestSnapshotRefusesToOverwrite`, `TestAReplicaRefusesEveryWrite`, `TestPullSnapshotInstallsABoard`,
`TestPullSnapshotRefusesJunk`, `TestPullSnapshotNeedsTheAdminToken`.

Known gap, recorded rather than hidden: the age is in the response headers and the log, not yet as a
visible banner on the page.

## Task 6 — `/dist` and signing (done, with a deviation)

**Files:** `internal/board/dist.go`, `scripts/sign-release.sh`, `cmd/nsm/main.go`.

The manager serves `GET /dist/manifest` and `GET /dist/{os}/{arch}/nsm`, bearer-authenticated (never
public: the artifacts reveal the fleet). `nsm agent install --version X` fetches, verifies the
signature against a key pinned at install time, and replaces the binary atomically.

**Decision taken: ed25519 via `crypto/ed25519`, not minisign.** The spec (§18) says minisign; the
verifier, though, lives in the agent — the thing installed on a Pi that should need nothing installed
beside it — and in the manager, which is stdlib-only by rule. A minisign verifier would mean either a
second dependency or a re-implementation of its signature format in this repo. Ed25519 over the exact
bytes of `SHA256SUMS` is the same guarantee with no new dependency, and an operator can still verify
by hand with `sha256sum -c`. The format is coreutils, not a new one.

The private key never goes on the manager: a signature the manager could forge protects nobody from
a compromised manager. `nsm dist keygen` refuses to overwrite an existing key, because a new key
replacing the old one invalidates every agent that pinned it, and the operator would find out at 3am.

Acceptance as built: `TestSignVerifyRoundTripAndTamper`, `TestParseSumsReadsTheBuildOutput`,
`TestParseSumsRefusesWhatItCannotFullyRead`, `TestTwoArtifactsForOneTargetIsRefused`,
`TestCheckOrderIsSignatureFirst`, `TestKeysHaveExactlyOneLength`, `TestDistNeedsTheAdminToken`,
`TestDistServesWhatTheChecksumFileNames`, `TestDistSaysSoWhenNoReleaseIsConfigured`,
`TestTheServedReleaseVerifies`, `TestDistSignAndVerifyThroughTheCLI`, `TestDistSignRefusesABogusKey`,
`TestKeygenRefusesToReplaceAKey`, `TestUpgradeReplacesTheBinaryAfterBothChecks`,
`TestUpgradeRefusesATamperedArtifact`, `TestUpgradeRefusesAnotherKeyAndAMissingToken`.

Acceptance (once decided): `TestTheManifestNamesEveryTarget`, `TestDistRequiresTheAdminToken`,
`TestAnUnpinnedKeyIsRefusedAtInstall`.

## What M6 does not do

- No dynamic model discovery on the Pi; the endpoint list is the manager's.
- No write-through replica (see the memo: a Pi that can write is split-brain on the LAN).
- No Windows service until `nsm agent install` has a Windows unit to generate.
