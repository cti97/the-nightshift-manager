# The Night Shift Manager — M4 Implementation Plan (watches)

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the board itself notice something — on a schedule, every N minutes, or when a condition becomes true — and turn it into an ordinary work item.

**Architecture:** A watch is a row with a trigger, a schedule, an optional probe, and a template. A scheduler loop on the **manager** selects watches whose stored `next_fire_at` is due and, in one transaction, creates the item from the template, advances the schedule, and writes an event. Everything downstream — placement, claim, escalation, spend — is the machinery that already exists; a watch emits work, it does not run it.

**Tech Stack:** Go 1.24+, stdlib only, `modernc.org/sqlite`, migration 5.

**Spec:** `docs/superpowers/specs/2026-11-15-nightshift-manager-design.md` §5 (the `watches` table), §9 (placement is the only router), §14 (dashboard), §16 (failure matrix)

**Predecessors:** the M0/M1, M2 and M3 plans. M3's "Decisions settled before the first task" is required reading: its D6 (the reaper leaves parked items alone) and its grant rule are the two invariants this milestone's scheduler must not disturb.

## Decisions settled before the first task

M3's tasks went smoothly because its decisions were made in the plan rather than discovered inside a task. These are M4's.

**D1 — Firing is one transaction.** Creating the item, advancing `next_fire_at`, stamping `last_fired_at`, and writing the event happen together. A crash between any two of them either double-fires a watch or loses a fire, and both are invisible until someone counts items. The item and the event are written through the same `Execer` the rest of the board uses.

**D2 — `next_fire_at` is stored and authoritative; a missed window fires once.** The scan is `enabled=1 AND next_fire_at <= now`, served by an index. Being due is never recomputed from `last_fired_at` at scan time: a manager that was down for a day would then either fire every missed slot at once or silently drift. On every evaluation — fired or skipped — the schedule advances from *now*, so a week of downtime produces one catch-up emission, not 168.

**D3 — Cron is five fields, UTC, and a documented subset.** Minute, hour, day-of-month, month, day-of-week; `*`, `n`, `a-b`, `*/n`, comma lists, and three-letter month/day names. No seconds field (the scheduler ticks every 15s and a minute is the resolution the product needs), no `L`/`W`/`#`. Evaluation is UTC because every other timestamp on this board is, and per-watch time zones would mean shipping a tz database or trusting `TZ` — neither belongs in M4. The parser refuses what it does not implement rather than approximating it.

When one of day-of-month and day-of-week is `*`, the other decides. When **both** are restricted, both must match — an AND. Vixie cron ORs them, which is a quirk nobody means to rely on and which makes a schedule read differently from how it behaves; the plan pins the AND rule in a test, so the difference from Vixie is stated rather than inherited by accident.

**D4 — Interval is a Go duration, with a floor.** `90s`, `5m`, `1h` via `time.ParseDuration`, minimum one minute. Below that the scheduler is a busy loop, and a watch that fires more than once a minute is a cron expression's job.

**D5 — A condition watch is edge-triggered, and the edge survives a restart.** `probe` exit 0 means true. A watch that stays true emits **once**, on the false→true transition; the previous observation lives in `watches.last_result` (migration 5), not in a map on the manager, because a manager restart must not re-fire a condition that was already true. Interval and cron watches are level-triggered by their schedule; a probe, if present, is an additional gate.

**D6 — Dedupe and cooldown are different mechanisms with different owners.** `dedupe_window` (seconds, default 3600) is the system's floor between two emissions of one watch, measured from `last_fired_at`. `cooldown_until` is the operator's hold, set explicitly and never touched by a fire. They are separate for the same reason the spend pause has two owners (M2): clearing one must not silently clear the other. A fire checks both.

**D7 — A skipped evaluation is recorded, not silent.** A watch that is due but does not fire advances `next_fire_at` and writes `last_skip_at` + `last_skip_reason` (migration 5). It does **not** write an event per skip — that floods the spine with ticks — but the list route reports both, so "why hasn't it fired" is answerable without reading the manager's log. Silence is how a watch becomes a thing people stop trusting.

**D8 — The probe runs on the manager, as the admin's code.** The spec puts the scheduler on the manager so a probe sees the VPS, not a laptop. `probe` runs through `/bin/sh -c` with a 30s timeout, and its exit code is the observation; the last 4 KiB of combined output goes into the event payload on a fire and into `last_skip_reason` on a failure. This means the admin token can execute code on the manager — it already can create items and read every brief, and this is a deliberate extension of that trust, documented in §16 and in "What M4 deliberately does not do". A watch that needs to inspect a laptop must emit an item with the right `needs` and let placement route it (spec §5).

**D9 — A paused board still fires watches.** The pause stops *issuance*, not observation: `Claim` already returns nothing while paused, so a fired item simply queues and the event records that the board saw the thing. Suppressing the fire instead would make the pause rewrite history — a condition that became true while the board was paused would never be recorded at all. A long pause therefore accumulates queued items, which is visible on `/board` and is the operator's cue.

**D10 — There is no delete.** A watch can be disabled and held, but its row and its emissions stay. A deleted watch is a hole in the audit trail exactly when someone asks why a hundred items exist.

## Global Constraints

- **Module path** `github.com/cti97/the-nightshift-manager`; **Go `1.24`**; **`CGO_ENABLED=0`**; no new dependencies; stdlib `testing` only.
- **`time.Now()` appears in exactly one file, `internal/board/clock.go`.**
- Every state change writes an `AppendEvent` in the same transaction as the change.
- Handlers never panic; JSON error envelope `{"error":{"code","message"}}`.
- **A watch emits work; it never executes it.** Nothing in the watch path may run a model, hold a lease, or touch a run.
- **Do not disturb the parked-item rules** (M3): the scheduler must not touch `needs_approval`, must not consume grants, and must not re-price a run.
- Do not weaken an existing test.
- **A comment must be checked against the code beside it.** M3's commits caught two comments that described a different design than the line under them; assume this milestone will produce more.

## Task 1: Migration 5 and the watch record

**Files:** `internal/board/schema5.sql`, `internal/board/db.go` (the migrations list), `internal/board/watches.go` (new).

```sql
CREATE TABLE watches (
  id             TEXT PRIMARY KEY,
  name           TEXT NOT NULL UNIQUE,
  trigger        TEXT NOT NULL CHECK (trigger IN ('cron','interval','condition')),
  schedule       TEXT,
  probe          TEXT,
  template       TEXT NOT NULL,
  dedupe_window  INTEGER NOT NULL DEFAULT 3600,
  cooldown_until INTEGER,
  enabled        INTEGER NOT NULL DEFAULT 1,
  last_fired_at  INTEGER,
  next_fire_at   INTEGER,
  last_result    INTEGER,
  last_skip_at   INTEGER,
  last_skip_reason TEXT,
  created_at     INTEGER NOT NULL
);
CREATE INDEX idx_watches_due ON watches(next_fire_at) WHERE enabled = 1;
```

The spec's table (§5) plus four columns M4's decisions require: `last_result` (D5's edge state), `last_skip_at` and `last_skip_reason` (D7's answer), and `created_at` (every other table has one). The migration comment says so, and says that `template` is JSON with `{title, brief, needs, priority, max_attempts}`.

**The type:**

```go
// Watch is one standing trigger: a schedule, an optional observation, and the
// item it emits. It never holds work itself — firing creates an ordinary
// work_item and lets placement route it (spec §5).
type Watch struct {
	ID             string   `json:"id"`
	Name           string   `json:"name"`
	Trigger        string   `json:"trigger"`  // cron | interval | condition
	Schedule       string   `json:"schedule"` // cron expression or Go duration; empty for condition
	Probe          string   `json:"probe,omitempty"`
	Template       WatchTemplate `json:"template"`
	DedupeWindow   int      `json:"dedupe_window"`
	CooldownUntil  *int64   `json:"cooldown_until,omitempty"`
	Enabled        bool     `json:"enabled"`
	LastFiredAt    *int64   `json:"last_fired_at,omitempty"`
	NextFireAt     *int64   `json:"next_fire_at,omitempty"`
	LastResult     *bool    `json:"last_result,omitempty"`
	LastSkipAt     *int64   `json:"last_skip_at,omitempty"`
	LastSkipReason string   `json:"last_skip_reason,omitempty"`
	CreatedAt      int64    `json:"created_at"`
}

// WatchTemplate is what a fire turns into. Needs goes through caps.Parse at
// create time, so a typo in a watch is refused when the operator types it, not
// when the item is claimed at 03:00.
type WatchTemplate struct {
	Title       string   `json:"title"`
	Brief       string   `json:"brief"`
	Needs       []string `json:"needs"`
	Priority    int      `json:"priority"`
	MaxAttempts int      `json:"max_attempts"`
}
```

**Acceptance:**
- `TestMigrationFiveAddsTheWatchesTable` — a v4 database gains the table, the index, and the four extra columns; `user_version` is `schemaVersion`, not a literal.
- `TestAVersionFiveDatabaseRefusesAnOlderBinary` — build the fixture with `migrate(ctx, raw, migrations[:5])` (M3's lesson: never `Open` a fixture whose version you are about to assert).
- `TestWatchTemplateRoundTrips` — encode, store, read back byte-identical, including empty `needs` as `[]`.

## Task 2: Schedules

**Files:** `internal/board/schedule.go` (new), `internal/board/schedule_test.go` (new).

Three functions, no database:

```go
// ParseSchedule validates one trigger's schedule and returns the next fire time
// after `from`. A condition watch has no schedule of its own: its next fire is
// the next scheduler evaluation, which the caller supplies.
func ParseSchedule(trigger, schedule string, from int64) (next int64, err error)

// NextFire is the same computation for a watch already parsed, used by the
// scheduler when it advances the schedule after a fire or a skip.
func NextFire(trigger, schedule string, from int64) (int64, error)
```

Cron: five fields, minute resolution, UTC, the subset D3 names. `*/n` and `a-b/n` are supported on every field; names are accepted on month and day-of-week. The parser expands each field into a sorted set, then searches forward from `from+60s` for a minute whose day-of-month **and** day-of-week both match; a field that is `*` matches every value, so the rule is ordinary conjunction and the AND-vs-Vixie difference D3 states falls out of it rather than being special-cased.

Interval: `time.ParseDuration`, ≥ 1 minute, next = `from + interval`.

Condition: no schedule; `NextFire` returns `from` (the next tick evaluates it).

**Acceptance:**
- `TestCronFiresAtTheNextMatchingMinute` — table-driven: `*/5`, `0 * * * *`, `30 2 * * *`, `0 0 1 * *`, `0 0 * * 1`, month names, lists, ranges.
- `TestCronIsUTCAndMinuteResolution` — a schedule whose local interpretation would differ; seconds are not a field and a 6-field expression is refused with a message naming the reason.
- `TestCronRefusesWhatItDoesNotImplement` — `L`, `W`, `#`, `@daily`, `*/0`, `60 * * * *`, and an empty field each error, and the error names the field and the token.
- `TestCronAcrossMonthAndYearBoundaries` — 31 January → 1 February, 29 February in a leap year, and a day-of-month that does not exist in the next month (`31 2 * * *` from 1 April → 1 May).
- `TestIntervalScheduleFloor` — `30s` is refused; `1m`, `90s`, `2h` are accepted; a malformed duration names the input.

## Task 3: Create, list, and hold a watch

**Files:** `internal/board/watches.go`, `internal/board/http.go`.

```
POST  /admin/watches        {name, trigger, schedule, probe, template, dedupe_window}
GET   /admin/watches        -> [Watch], oldest first, [] when none
PATCH /admin/watches/{id}   {enabled?, cooldown_until?}
```

Create validates everything a fire would otherwise discover late: the trigger is one of three; the schedule parses (Task 2) for cron and interval; a condition watch has a probe and no schedule; a non-condition watch may have either; `template.title` and `template.brief` are non-empty; `template.needs` goes through `caps.Parse`; `max_attempts` defaults to 3; `dedupe_window` is ≥ 0. `next_fire_at` is computed at create time from `clock.Now()`, so a new watch is due at its next slot rather than immediately.

PATCH is the operator's two levers: disable (stops firing, keeps history — D10) and hold (`cooldown_until`). Clearing a hold is an explicit `{"cooldown_until": 0}`; omitting the field leaves it alone, which is what distinguishes "clear" from "don't touch" and is why the field is a pointer on the request type.

**Acceptance:**
- `TestCreatingAWatchComputesItsFirstFire` — an interval watch created at T has `next_fire_at = T + interval`.
- `TestAConditionWatchNeedsAProbeAndNoSchedule` — each half refused with a message naming the rule.
- `TestAWatchTemplateIsValidatedAtCreate` — empty title, unknown capability, negative priority each refused; nothing is written.
- `TestTheWatchListIsOldestFirstAndEmptyIsNotNull` — and the JSON carries `next_fire_at`, `last_fired_at`, `last_skip_*`, `last_result`.
- `TestDisablingAWatchStopsItWithoutDeletingIt` — `enabled=0`, row still present, still listed.
- `TestHoldingAWatchIsOperatorState` — setting `cooldown_until` and then firing must not clear it (D6); `0` clears it; omitting it leaves it.

## Task 4: The fire

**Files:** `internal/board/watches.go`.

```go
// Fire takes a due watch and emits its item, in one transaction (D1). BEGIN
// IMMEDIATE plus an in-transaction re-read is the guard: a fire always advances
// next_fire_at, so a second caller holding the old token is refused, and the
// serialized writer is what makes that refusal atomic. The SQL statement also
// requires enabled=1 AND next_fire_at <= now, because Fire does not trust its
// scanner — a scheduler bug must not emit items early. Two further clauses
// (next_fire_at = ? and last_fired_at < now) were written, found unreachable, and
// removed: an unreachable guard is a mutation nobody can catch.
func Fire(ctx context.Context, db *sql.DB, clock Clock, watchID string, observedNextFire int64) (FireResult, error)
```

One transaction: re-read the watch; re-check `enabled`, `next_fire_at == observedNextFire`, cooldown, dedupe, and the probe result (Task 6); create the `work_items` row with `created_by = "watch:<id>"`; set `last_fired_at`, `next_fire_at = NextFire(now)`, `last_result`; `AppendEvent(actor "watch:"+id, entity "watch", type "fired", payload {item, trigger, schedule, probe_exit})`.

`FireResult` says what happened: `Fired bool`, `ItemID string`, `Skipped string` (the D7 reason). A skipped fire still advances the schedule and writes `last_skip_*`, in its own transaction.

**Acceptance:**
- `TestFiringEmitsAnItemWithTheTemplate` — title, brief, needs, priority, `created_by = "watch:<id>"`, status `queued`.
- `TestFiringAdvancesTheScheduleAndStampsTheFire` — `last_fired_at` = now, `next_fire_at` = next slot, one `fired` event naming the item.
- `TestAStaleScanCannotFireTwice` — call `Fire` twice with the same `observedNextFire`: the second is skipped and no second item exists.
- `TestADisabledWatchDoesNotFire` and `TestASettledItemIsNotTouched` (the fire path never writes an existing item, a run, or a grant).

## Task 5: Dedupe, cooldown, and the skip record

**Files:** `internal/board/watches.go`.

`Fire` checks, in this order: enabled → due (`next_fire_at == observed`) → cooldown (`cooldown_until > now`) → dedupe (`last_fired_at + dedupe_window > now`) → probe. The first check that refuses wins and its text becomes `last_skip_reason`; the schedule still advances, and `last_skip_at` is stamped. The order is part of the contract: "held by the operator" must win over "deduped", or an operator who holds a watch would read the wrong reason for a day.

**Acceptance:**
- `TestACooldownSkipsTheFireAndSaysSo` — no item, `last_skip_reason` names the hold and its expiry, `next_fire_at` advanced.
- `TestADedupeWindowSkipsAFireInsideTheWindow` and `TestTheWindowDoesNotSkipAFireAfterIt`.
- `TestTheSkipReasonNamesTheFirstRefusal` — cooldown + dedupe both true; the reason is the cooldown.
- `TestASkipWritesNoEventPerTick` — ten consecutive skips produce no `fired` events and no flood of `skipped` events; the row's `last_skip_*` carries the history.

## Task 6: The probe and the condition edge

**Files:** `internal/board/watches.go`, `internal/board/probe_watch.go` (new).

```go
// runWatchProbe runs one watch's shell command on the manager (D8), bounded and
// with its output captured. The exit code is the observation: 0 is true, any
// other is false, and a timeout is neither — it is a failed observation, which
// must not fire and must not flip a condition's state.
func runWatchProbe(ctx context.Context, command string, timeout time.Duration) (exit int, tail string, timedOut bool)
```

For a **condition** watch: `true` on a false→true edge fires; `false` records `last_result=false` and does not; a timeout records a skip with the reason and leaves `last_result` alone (the observation did not happen). For **cron/interval** watches with a probe: `false` is a skip with the reason, `true` proceeds to the dedupe check.

The probe runs with the manager's working directory, a scrubbed environment (`PATH` only), and a 30s cap. Its output is truncated to 4 KiB at a **rune** boundary. That differs from the shell tool, which caps bytes (`cappedWriter`): the probe's tail is stored in an event payload, JSON must carry valid UTF-8, and a half rune would reach the audit trail as U+FFFD.

**Acceptance:**
- `TestAConditionFiresOnTheRisingEdgeOnly` — true, true, true produces one item; false→true produces a second.
- `TestAConditionSurvivesARestart` — `last_result` is read from the row, not from memory: a fresh `Fire` call against a watch stored with `last_result=true` does not fire.
- `TestAFailedProbeDoesNotFire` — exit 1 produces a skip naming the exit code and the output tail, and no item.
- `TestAProbeTimeoutIsNotAFalseObservation` — a timed-out probe leaves `last_result` unchanged and writes a skip naming the timeout.
- `TestProbeOutputIsTruncated` — a command that prints 1 MiB puts 4 KiB in the payload.

## Task 7: The scheduler loop

**Files:** `internal/board/watches.go`, `cmd/nsm/main.go`.

```go
// RunWatches ticks forever; cancel ctx to stop it. One pass scans due watches,
// fires each, and reports what it did. One bad watch must not stop the pass
// (M1's reaper rule): its error is collected and the rest run.
func (s *Server) RunWatches(ctx context.Context, every time.Duration)
```

The manager starts it next to `RunReaper` (15s cadence; the reaper's 30s is about leases, this is about minutes). The scan is `SELECT id, next_fire_at FROM watches WHERE enabled=1 AND next_fire_at IS NOT NULL AND next_fire_at <= ?` — ids and the observed value only; everything else is re-read inside `Fire`'s transaction, because anything read in the scan can be stale by the time the write happens (the reaper's rule, applied again).

**Acceptance:**
- `TestTheSchedulerFiresEveryDueWatchInOnePass` — three watches, one due, one held, one in the future.
- `TestOneBadWatchDoesNotStopThePass` — a watch whose probe cannot be executed errors; the due watch after it still fires, and the result reports both.
- `TestAPausedBoardEmitsButDoesNotIssue` — a fire during a pause still creates the item (D9); `Claim` returns nothing while paused, so it waits. The test asserts both halves, so the rule cannot be "simplified" into suppressing the emission.
- `TestTheSchedulerDoesNotTouchParkedItems` — a `needs_approval` item is untouched by a full pass (M3 D6).

## Task 8: The list answers "why isn't it firing"

**Files:** `internal/board/watches.go`, `internal/board/http.go`.

`GET /admin/watches/{id}` returns the watch plus a derived `state` sentence, composed in this order from what is stored: disabled; held until T; overdue (next_fire_at < now, so the scheduler is not running); waiting for the next slot at T; last skipped at T because R. This is the watch equivalent of `/why`, and it is a read: it writes nothing (the `/why` rule).

**Acceptance:**
- `TestAWatchStateNamesTheNextSlot` and `TestAWatchStateNamesAnOverdueSchedule` — the second is the one that matters: a watch due ten minutes ago whose row still says so is a manager that is not running, and the sentence has to say that rather than "waiting".
- `TestAWatchStateNamesTheHoldBeforeTheSchedule` — held and overdue: the hold is the answer.
- `TestReadingAWatchWritesNothing` — no events, no row changes.

**Note after implementation (two cases the wording above did not cover):**

- **Overdue needs a grace.** "next_fire_at < now" is true for every watch for up to one
  scheduler tick, so the literal rule would call a healthy manager stopped for fifteen
  seconds per slot. `watchStaleAfter` (2 minutes, eight ticks) is the line between "the
  next pass will take it" and "the scheduler is not running or is stuck".
- **A condition watch is never explained by its slot.** Its `next_fire_at` is always
  "now" by design, so the overdue rule would read a perfectly healthy condition as a
  stopped scheduler. It is explained by its last observation and its age — which is
  knowable because every evaluation writes a skip or a fire.
- The list (`GET /admin/watches`) carries the same sentence per row: an operator scans
  the list, and a per-row GET would make the page N+1.

## Task 9: `nsm watch add/list/hold`

**Files:** `cmd/nsm/main.go`.

`nsm watch add --name nightly --every 24h --title "…" --brief "…" --needs agentic`, `nsm watch add --cron "30 2 * * *" …`, `nsm watch list`, `nsm watch hold <name> --for 6h` / `--clear`. The admin token comes from the environment, never a flag (M3's rule). `watch list` prints the state sentence from Task 8, so the terminal and the API cannot disagree about why a watch is quiet. `hold --for` is parsed as a duration and sent as an absolute `cooldown_until`, because the CLI's clock is not the board's.

**Acceptance:**
- `TestWatchAddRequiresATriggerAndATemplate` — neither `--every` nor `--cron`; missing title; unknown capability: each exits 2 with the reason and creates nothing.
- `TestWatchListPrintsTheState` — a held watch reads "held until …", an overdue one reads "overdue".
- `TestWatchHoldSetsAndClears` — and the token is never a flag (`--token` does not parse).

**Note after implementation:**

- `--brief` is required too: the board refuses a template without one (the brief is what
  the executor reads when the item runs), and the CLI says so before the request rather
  than relaying a 400.
- Exit codes are split by cause: a 4xx (bad input, name taken) exits 2, a 5xx or an
  unreachable board exits 1. `adminCall` carries the status so `exitFor` can tell them
  apart, and a test pins the split.
- `watch hold` resolves the name through the list — watch names are unique, so this needs
  no new API — and a wrong name prints the names that do exist.

## What M4 deliberately does not do

- No per-watch time zones. Cron is UTC (D3); a watch that needs local time emits an item whose brief says so.
- No cron seconds or the `L`/`W`/`#` extensions (D3). The parser refuses them by name.
- No watch deletion (D10), no versioned templates, no templating language inside `title`/`brief` beyond what `POST /admin/items` already accepts.
- No probe on a node: the probe is manager-side code (D8). A watch that needs a laptop's filesystem emits an item with `needs`.
- No retry of a failed probe inside one tick, and no alerting on repeated probe failures beyond `last_skip_reason` — an alerting channel is M6's `/dist`-era work, not this.
- No watches on `needs_approval` items, threads, or runs: a watch emits items, and the rest of the board treats them like any other.
